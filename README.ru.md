# shaverma_adminka

*[Read this in English](README.md)*

Сервис административной панели управления (control-plane) для проекта
`shaverma`.

Этот репозиторий **независим** от основного репозитория `shaverma`: он
не импортирует код shaverma, не зависит от его моделей и не
модифицируется изменениями в нём. Он подключается к той же физической
базе данных `system_db`, но владеет и работает только со своими
собственными таблицами `admin_*`.

## Текущий охват

- Backend на FastAPI с двухфакторным (пароль + Telegram OTP) входом
  администратора, серверными сессиями и журналом аудита.
- Минимальный, полностью статический/независимый frontend: процесс
  входа, дашборд со списком backend-сервисов shaverma и их актуальным
  статусом в systemd, редактор `.env` для каждого сервиса и мастер для
  развёртывания нового сервиса «с нуля».
- Безопасный, универсальный слой выполнения подпроцессов (`app/system`)
  и реальные возможности, построенные поверх него: запуск/остановка
  systemd-юнита backend'а инстанса shaverma; чтение/запись
  принадлежащего root файла `.env` этого инстанса; и полный пайплайн
  создания нового сервиса — подготовка дерева каталогов, размещение
  загруженного кода, запуск отдельного скрипта выдачи учётных данных
  проекта «bot», сборка его frontend'а и запись конфигурации nginx +
  systemd — каждое действие через собственный узко ограниченный
  привилегированный хелпер.

Он намеренно **не** реализует: роли/права администраторов,
регистрацию/CRUD/CLI администраторов или любые эндпоинты сверх
перечисленных выше, которые управляли бы Ubuntu-хостом (произвольный
деплой/редеплой кода *существующего* сервиса, git pull, docker, логи,
общий файловый менеджер, shell/терминал или что-то подобное). Это
остаётся вне охвата до более поздней стадии, которая будет строиться
поверх этого фундамента. Мастер создания нового сервиса также
намеренно оставляет несколько шагов ручными — см. раздел «Мастер
развёртывания нового сервиса» ниже за подробностями, что именно и
почему.

## Стек технологий

- Backend: Python 3.12+, FastAPI, SQLAlchemy 2.x, Alembic, PyMySQL,
  pydantic-settings, pwdlib (Argon2id), httpx.
- Frontend: статические HTML/CSS/vanilla JS, без сборки, без привязки
  к фреймворку со стороны backend'а (backend — это простой JSON API,
  который позже можно сочетать с любым frontend'ом).

## Локальный запуск backend'а

```bash
cd backend
uv venv --python 3.12 .venv
uv pip install -e ".[dev]" --python .venv/bin/python
cp ../.env.example .env   # затем заполните реальными значениями
.venv/bin/uvicorn app.main:app --reload --host 127.0.0.1 --port 8100
```

(Обычный `pip install -e ".[dev]"` в venv на 3.12 тоже подойдёт; `uv`
просто быстрее.)

## Миграции базы данных

Alembic настроен с собственной историей миграций, полностью
независимой от миграций проекта shaverma, даже несмотря на то, что оба
работают с одной и той же `system_db`:

- миграции лежат в `backend/migrations`, а не в корне репозитория;
- таблица отслеживания версий Alembic называется
  **`admin_alembic_version`** (а не стандартная `alembic_version`), так
  что она никогда не может конфликтовать или быть перепутана с
  собственной историей Alembic проекта shaverma в той же базе данных;
- `migrations/env.py` ограничивает autogenerate только таблицами с
  именами `admin_*`, так что `alembic revision --autogenerate` никогда
  не предложит изменить или удалить таблицу, которой этот проект не
  владеет.

```bash
cd backend
.venv/bin/alembic upgrade head
```

## Администраторы

Есть ровно **два** администратора. Они полностью равноправны — в этой
системе намеренно нет ролей, прав или групп.

Администраторы **не** создаются через API, frontend или CLI — этого
специально не существует. Они добавляются напрямую в `admin_users`
вручную. Чтобы сгенерировать корректный хеш пароля Argon2id для
ручного `INSERT`:

```bash
cd backend
.venv/bin/python -c "
from app.auth.password import hash_password
print(hash_password('the admin\'s real password'))
"
```

Затем вставьте строку примерно такого вида:

```sql
INSERT INTO admin_users (username, password_hash, telegram_user_id, is_active)
VALUES ('alice', '<хеш из предыдущего шага>', '<telegram user id алисы>', 1);
```

`telegram_user_id` — это числовой Telegram user id администратора, **а
не** его номер телефона и не отдельный «chat id»: для приватного чата
бот<->пользователь это численно одно и то же значение, так что этого
одного поля достаточно для доставки сообщений. Получить его можно,
например, попросив администратора один раз написать боту и прочитав
`message.from.id` из ответа `getUpdates` бота (один лишь номер
телефона нельзя использовать для отправки сообщения пользователю
Telegram через Bot API — такого поиска в этом API не существует).

## Telegram-бот

Панель администратора использует **свой собственный выделенный
Telegram-бот**, отдельный от клиентского бота shaverma. Создайте бота
через @BotFather, поместите его токен в `ADMIN_TELEGRAM_BOT_TOKEN` и
никогда не используйте здесь повторно токен основного продуктового
бота. На данный момент бот делает ровно одну вещь:
`TelegramClient.send_login_code(telegram_user_id, code)`.

## Процесс аутентификации

```
POST /api/v1/auth/login/start   {username, password}
  -> {challenge_id, expires_at}   (OTP отправляется через Telegram)

POST /api/v1/auth/login/verify  {challenge_id, code}
  -> устанавливает HttpOnly-куку сессии + CSRF-куку

GET  /api/v1/auth/me            -> текущий администратор
POST /api/v1/auth/logout        -> требует заголовок X-CSRF-Token
```

Сессии хранятся на стороне сервера (таблица `admin_sessions`); браузер
хранит только непрозрачный случайный токен в HttpOnly-куке с
SameSite=Strict (Secure в продакшене). В базе данных хранится только
SHA-256-дайджест этого токена. JWT нет, и ничего, связанного с
авторизацией, никогда не попадает в `localStorage`.

Защита от CSRF использует паттерн double-submit-cookie:
`login/verify` также устанавливает не-HttpOnly куку `admin_csrf`,
значение которой должно быть продублировано в заголовке
`X-CSRF-Token` при запросах, меняющих состояние (`/auth/logout` и
`/services/{id}/start`/`.../stop`).

## Журнал аудита

Каждое событие аутентификации и каждое действие управления
сервисом/`.env` записывается в `admin_audit_events`:
`auth.login.password_failed`, `auth.login.otp_requested`,
`auth.login.otp_failed`, `auth.login.success`, `auth.logout`,
`service.start`, `service.stop` (target = разрешённое имя юнита, плюс
код завершения и длительность), `env.read`, `env.write` (target =
`system_name`; `parameters_json` у `env.write` хранит только *имена*
ключей, которые были добавлены/удалены/изменены, например
`{"added": ["NEW_KEY"], "removed": [], "changed": ["FOO"]}` — никогда
значения). `env.read` логируется и при успехе, а не только при
ошибке, поскольку просмотр секретов сервиса сам по себе заслуживает
записи в журнал аудита. `app/audit/service.py` активно вычищает любой
ключ параметра, который выглядит чувствительным (`password`, `otp`,
`token`, `secret`, ...) перед записью — пароли, хеши паролей, коды
OTP, токены сессий, токен Telegram-бота и значения `.env` нигде не
логируются.

## Слой системных команд

`app/system/executor.py` предоставляет `CommandExecutor` — безопасную
обёртку вокруг `asyncio.create_subprocess_exec` (никогда не строка
для shell — исполняемый файл и каждый аргумент всегда передаются как
отдельные элементы, поэтому поверхности для shell-инъекций не
существует по конструкции). Поддерживает таймаут, ограниченные
`cwd`/окружение, захват stdout/stderr с лимитом и завершение зависшего
процесса, возвращая структурированный `CommandResult`.

`app/system/registry.py` определяет протокол `SystemAction` и
`ActionRegistry`, в который регистрируются действия по имени. В API
намеренно нет универсальной точки входа `execute(command: str)` —
каждая возможность является явным, именованным, индивидуально
проверенным `SystemAction`. Полный набор, зарегистрированный сегодня
(`app/system/service_actions.py` + `app/system/env_actions.py`,
подключаются один раз при старте в `app/system/bootstrap.py`):

| имя              | что выполняется                               | привилегии |
|------------------|------------------------------------------------|------------|
| `service.status` | `systemctl show <unit> --property=...`          | нет        |
| `service.start`  | `sudo systemctl start <unit>`                   | sudoers    |
| `service.stop`   | `sudo systemctl stop <unit>`                    | sudoers    |
| `env.read`       | `sudo env_file_helper.py read <system_name>`    | sudoers    |
| `env.write`      | `sudo env_file_helper.py write <system_name>` (новое содержимое через stdin) | sudoers |

`app/system/service_control.py` — это слой над реестром
(`API -> ServiceControlService -> ActionRegistry -> CommandExecutor`):
он превращает значение `services.system_name` в имя юнита
(`{system_name}-backend.service`), сначала проверяет это значение по
безопасному шаблону идентификатора и определяет «существует ли этот
юнит» по `LoadState` из `systemctl show` (`not-found` -> не
существует — сообщается в API/UI именно так, а не как ошибка, и
start/stop даже не пытаются вызвать `sudo` для юнита, которого не
существует). `app/system/env_file_control.py` — аналогичный слой для
файлов `.env` — см. следующий раздел.

`CommandExecutor` также умеет передавать байты в stdin дочернего
процесса (`CommandSpec.stdin`, используется `env.write` для передачи
нового содержимого файла хелперу) — и даёт дочернему процессу
**совсем никакого** stdin (`DEVNULL`), когда `stdin` равен `None`,
вместо того чтобы молча наследовать stdin самого серверного процесса,
так что запущенная команда никогда случайно не заблокируется на нём.

## Панель управления сервисами

`GET /api/v1/services` возвращает список всех строк собственной
таблицы `services` shaverma, у которых установлен `system_name`. Он
намеренно **не** обращается к systemd вовсе — это простое чтение из
БД, так что листинг остаётся дешёвым независимо от количества
подключённых сервисов, — поэтому `status` в каждой строке возвращается
как `null`, и панель окрашивает её только на основе сохранённого флага
`is_active` (с подсказкой «не проверено»), а не на основе актуального
состояния.

Три действия напрямую обращаются к systemd и возвращают актуальный
статус этой строки, и все три требуют аутентифицированной сессии и
CSRF-заголовка, и все логируются в аудит точно так же, как эндпоинты
аутентификации:

- `POST /api/v1/services/{id}/start` / `.../stop` управляют юнитом
  backend'а (`service.start` / `service.stop`, с именем юнита, кодом
  завершения и длительностью). При успехе также записывают
  `services.is_active` в соответствие (`True` после старта, `False`
  после остановки).
- `POST /api/v1/services/{id}/check-status` (`service.check_status`)
  не меняет ничего в самом юните — он только читает его актуальный
  статус тем же непривилегированным `systemctl show`, что и два других
  действия, — но если это расходится с сохранённым `is_active`, он
  исправляет `is_active` в соответствие и записывает это в событие
  аудита (`parameters.corrected`).

`is_active` — единственный источник истины, из которого рендерится
список; панель — это то, что поддерживает его достоверность через эти
три действия. Он всё ещё может отставать от реальности между
вызовами, например если юнит был запущен/остановлен, или сам
`is_active` был изменён собственной бизнес-логикой shaverma, в обход
панели.

adminka не владеет таблицей `services` — она принадлежит репозиторию
[shaverma](https://github.com/Shira-Artem/shaverma). `services.system_name`
(`varchar(30)`, nullable, без уникального ограничения) уже существует
в `system_db`, так что для его добавления здесь миграция не
понадобилась. `app/external/models.py` маппит только те столбцы,
которые действительно нужны adminka (`id`, `name`, `is_active`,
`system_name`, `server_local_port`, ...) на декларативную базу,
полностью отдельную от собственной `Base` adminka — она никогда не
входит в `target_metadata` в `migrations/env.py`, так что в этом
проекте нет ни одной миграции, которая могла бы создать, изменить или
удалить `services`.

## Редактор .env

Каждый инстанс shaverma развёрнут как
`{некая корневая папка}/{system_name}/`, принадлежит root, содержит
`dist/` и `backend/` (принадлежат ОС-пользователю, от имени которого
работает этот инстанс) и принадлежащий root файл `.env`. Собственный
процесс adminka непривилегирован и не может читать или писать этот
файл напрямую, поэтому это проходит через узко ограниченный
привилегированный хелпер, а не через универсальный `sudo cat`/`sudo
tee` (что позволило бы любому, кто обладает правом sudoers, читать
или перезаписывать произвольный файл, принадлежащий root):

- `backend/scripts/env_file_helper.py` -- небольшой самостоятельный
  скрипт, разворачивается отдельно (принадлежит root, режим `700`,
  **не** входит в собственный путь импорта Python-пакета adminka). Он
  принимает только `read <system_name>` / `write <system_name>`
  (новое содержимое через stdin для `write`), но никогда путь; реальный
  путь `{root}/{system_name}/.env` строится из константы
  `PROJECT_ROOT`, зашитой в сам скрипт, так что ни один аргумент,
  переданный вызывающей стороной, не может привести к выходу за
  пределы этого корня. `write` заменяет файл атомарно (запись во
  временный файл в той же директории, `os.replace`) и сохраняет
  владельца/группу/режим существующего файла — или использует
  `root:root 0600` по умолчанию для совершенно нового файла.
- `app/system/env_file_control.py` владеет форматом текста `.env` на
  стороне приложения: парсинг сохраняет комментарии и пустые строки (и
  их позицию), так что редактирование через табличный UI не приводит к
  молчаливой потере собственных заметок оператора — добавляются,
  меняются или удаляются только строки вида `KEY=VALUE`. Ключ должен
  соответствовать `^[A-Za-z_][A-Za-z0-9_]*$`; значением может быть
  любая строка, помещающаяся в одну строку (без `\n`/`\r`/NUL).
  Отсутствие файла `.env` для в остальном реального инстанса
  считывается обратно как пустой список, а не как ошибка, так что
  панель всё равно можно использовать для его создания; запись для
  `system_name` без директории инстанса вовсе возвращает 409, в том же
  духе «не существует, так и сообщить», что и панель управления
  сервисами выше.

API: `GET /api/v1/services/{id}/env` возвращает разобранные записи
(плюс отображаемый только для показа разрешённый путь, если задан
`INSTANCES_ROOT_DIR`). `POST /api/v1/services/{id}/env` принимает
*полный* желаемый список `{key, value}` — ключ, отсутствующий в нём,
удаляется, новый — добавляется, изменённое значение — обновляется — и
требует заголовок CSRF, как и любой другой эндпоинт, меняющий
состояние. Версионирования/блокировки при одновременном редактировании
нет — при двух администраторах это принятое ограничение «последняя
запись побеждает», а не то, что эта стадия пытается решить.

Frontend: `service-env.html` (ссылка с кнопки ".env" в каждой строке
дашборда) — это настоящая таблица поле/значение, а не сырое текстовое
поле — добавление, редактирование, удаление, плюс переключатель
«показать значения» (по умолчанию скрыты, поскольку именно здесь
хранятся секреты) и подтверждение перед сохранением, если удаляется
какая-либо переменная.

## Мастер развёртывания нового сервиса

`new-service.html` проводит администратора через превращение метки
домена в полностью работающий инстанс shaverma. Это **один эндпоинт
на шаг, а не одна all-or-nothing транзакция** -- побочные эффекты
затрагивают БД, файловую систему, *собственные записи в базу данных
отдельного проекта* (см. «выдача учётных данных» ниже), nginx и
systemd, и нет способа откатить всё это атомарно как группу, если шаг
5 провалился после того, как шаги 1-4 уже прошли успешно. Вместо этого:

- каждый шаг независимо вызываем и безопасен для повтора — он либо
  проверяет актуальное состояние перед действием (например,
  `instance.install_backend` требует, чтобы `instance.create_tree`
  действительно уже отработал), либо полностью заменяет, а не
  дописывает (повторный запуск шага nginx обновляет существующий блок
  на месте; шаг systemd полностью переписывает файл юнита);
- `GET /api/v1/services/{id}/provision/status` никогда не доверяет
  закэшированному флагу «шаг N выполнен» -- он каждый раз заново
  выводит статус каждого шага из реального состояния (существует ли
  директория и есть ли в ней содержимое? установлен ли в `.env`
  `SYSTEM_GATEWAY_API_KEY`? есть ли в конфигурации nginx блок-маркер
  этого сервиса? активен ли юнит systemd?) -- та же философия, что и у
  актуального статуса systemd на дашборде;
- каждый шаг логируется в аудит по отдельности, независимо от успеха
  или неудачи.

### Шаги

1. **`POST /api/v1/services`** -- чисто работа с БД, без каких-либо
   побочных эффектов на файловую систему/systemd/nginx. Принимает
   заданную администратором метку домена третьего уровня (например,
   `индия`), имя, `system_name`, `is_active` (по умолчанию включено),
   `channels` (`telegram`/`max`, по умолчанию оба включены) и
   опциональные `bot_entry_key`/`client_bot_entry_key`.
   `app/provisioning/domain.py` строит `url` =
   `https://{label}.{SERVICE_DOMAIN_ZONE}` и `backend_base_url` =
   `https://api-{label}.{SERVICE_DOMAIN_ZONE}`, оба полностью
   закодированы по IDNA2008/punycode (через пакет `idna`, а не более
   старый встроенный кодек Python) -- так что кириллическая метка под
   кириллической зоной (`example-service.рф`) корректно проходит round-trip.
   `app/provisioning/service_creation.py` проверяет `url`,
   `system_name`, `bot_entry_key` и `client_bot_entry_key` на
   уникальность относительно существующих строк `services` *до*
   вставки, возвращая 409 с указанием конкретного поля, вместо того
   чтобы позволить всплыть `IntegrityError` из БД.
2. **`POST /services/{id}/provision/dirs`** -- `instance.create_tree`:
   идемпотентно создаёт `{root}/{system_name}/`, `dist/`, `backend/`
   (принадлежат `SERVICE_WORK_USER`).
3. **`POST /services/{id}/provision/upload`**
   (`multipart/form-data`, одно поле `file`) -- администратор
   отправляет zip-архив с папками `frontend/` и `backend/` на верхнем
   уровне. `app/provisioning/upload.py` распаковывает его в процессе
   средствами Python `zipfile` (никогда не через `unzip` в
   подпроцессе -- никакой поверхности для command-инъекций из
   содержимого zip-архива вообще), отклоняя обход путей, симлинки и
   архивы, превышающие лимит по размеру/количеству записей, *до* того,
   как что-либо распаковывается. Половина `backend/` затем
   перемещается в дерево инстанса через `instance.install_backend`;
   `frontend/` остаётся в собственной непривилегированной директории
   staging adminka (`INSTANCE_STAGING_DIR`) для следующего шага.
4. **`POST /services/{id}/provision/env`** -- запускает собственный
   скрипт выдачи учётных данных отдельного проекта «bot» (ниже), затем
   формирует и записывает полный `.env` нового инстанса через тот же
   самый `EnvFileControlService`/`env.write`, что использует ручной
   редактор. `DATABASE_URL`, `YOOKASSA_SHOP_ID` и
   `YOOKASSA_SECRET_KEY` намеренно оставлены пустыми -- см. «Что этот
   мастер НЕ автоматизирует» ниже -- и ответ содержит ссылку на
   `service-env.html`, чтобы заполнить их (или скорректировать что-то
   ещё) вручную.
5. **`POST /services/{id}/provision/frontend`** -- записывает
   подмножество `.env` с префиксом `VITE_` в исходники staged
   frontend'а, затем запускает там `npm install` и `npm run build`
   (см. «Модель привилегий npm install» ниже), после чего перемещает
   собранный `dist/` в дерево инстанса через `instance.install_dist` и
   удаляет staging-копию (исходники + `node_modules` + промежуточный
   вывод сборки) -- ничего из загруженного *исходного кода* frontend'а
   не переживает этот шаг, только собранный статический вывод.
6. **`POST /services/{id}/provision/nginx`** -- выделяет локальный
   порт, если у этого сервиса ещё нет своего (`services.server_local_port`
   -- единственный источник истины «уже занято», а не конфигурация
   nginx, которая лишь отражает это; `app/provisioning/port_allocation.py`
   выбирает первый свободный порт начиная с `SERVICE_PORT_RANGE_START`,
   который ещё не занят как `server_local_port` какой-либо другой
   строки и который `ss -Hltn` не сообщает как прослушиваемый --
   чтение прослушиваемых портов не требует привилегий). Повторный
   запуск этого шага переиспользует порт, уже сохранённый в строке,
   вместо выбора нового. Формирует два блока `server {}` этого сервиса
   (фронт + бэк), обёрнутых в пару маркеров
   `# adminka:service:{system_name}:begin/end`, и просит
   `NginxControlService` (`app/system/nginx_control.py`) вставить их
   или обновить -- см. «nginx: никогда никакой частичной правки» ниже
   о том, что это на самом деле делает.
7. **`POST /services/{id}/provision/systemd`** -- формирует файл юнита
   (`app/provisioning/systemd_template.py`; явно **без** `--reload` в
   `ExecStart` у `uvicorn` -- это флаг только для разработки,
   отслеживающий файлы, которому не место в продакшн-юните), записывает
   его через `systemd.write_unit` (который также выполняет
   `systemctl daemon-reload`, уже от root, внутри того же вызова
   хелпера), затем `service.enable_now` (`systemctl enable --now`, так
   что сервис одновременно запускается немедленно и переживает
   перезагрузку).

### Выдача учётных данных (проект «bot»)

Шаг 4 выполняет команду в **отдельной кодовой базе** -- не shaverma,
не в этом репозитории -- которая владеет генерацией
`SYSTEM_GATEWAY_API_KEY` / `SYSTEM_GATEWAY_SIGNING_SECRET` для сервиса
и записывает их в `system_db` через *собственную* SQLAlchemy-сессию
(adminka никогда не трогает эти столбцы сама). `app/provisioning/credentials_script.py`
встраивает фиксированный, проверенный Python-скрипт (переведённый из
shell heredoc в форму, которую `CommandExecutor` может запускать
напрямую -- он никогда не использует shell, поэтому не может
`source venv/bin/activate`; прямой вызов `{SERVICE_VENV_DIR}/bin/python`
даёт тот же эффект для одного подпроцесса, а `python -c` автоматически
добавляет текущую директорию в `sys.path`, так что только
`cwd=BOT_PROJECT_DIR` -- это то, что позволяет разрешиться `import
bot....`). Единственный переменный вход -- числовой id нового сервиса,
передаваемый через переменную окружения `SERVICE_ID`, никогда не
интерполируемый в текст скрипта. Здесь не используется sudo --
подтверждено, что собственный ОС-пользователь adminka уже имеет доступ
на чтение/выполнение к коду проекта bot и его общему venv.

### Модель привилегий npm install

`npm install`/`npm run build` выполняют произвольный код из
`package.json` и собственных lifecycle-скриптов зависимостей. Они
выполняются от имени **собственного ОС-пользователя adminka, в
`INSTANCE_STAGING_DIR`** -- никогда не от root и никогда внутри
принадлежащего root дерева инстанса; только готовый статический вывод
`dist/` переносится в это дерево, через `instance.install_dist`. Это
было осознанным выбором среди реальных альтернатив (запуск от имени
отдельного, ещё более изолированного пользователя ОС только для
сборки был другим серьёзно рассматриваемым вариантом) -- собственная
учётная запись adminka не является максимально низкопривилегированной
в любом случае (она обладает грантами sudoers ниже), так что если этот
компромисс когда-либо перестанет быть приемлемым, замена на отдельного
пользователя для сборки затронет только `app/provisioning/frontend_build.py`.

`node_bin_dir`/`NODE_BIN_DIR` должен быть конкретной версионированной
директорией bin/, к которой в противном случае разрешился бы
`nvm use 22` (например, `~/.nvm/versions/node/22.23.0/bin`) --
`CommandExecutor` никогда не подключает shell-функции nvm, поэтому сам
`nvm use` не может быть вызван.

### nginx: никогда никакой частичной правки

Повреждение *общего* конфигурационного файла nginx положило бы сразу
все развёрнутые сайты, а не только добавляемый. Поэтому
`NginxControlService.upsert_service_block` никогда просто не пишет и
надеется на лучшее: он читает текущую конфигурацию, вычисляет новое
содержимое в памяти (через шаблон вставки/замены на основе маркеров из
`app/provisioning/nginx_template.py` -- идемпотентный, так что
повторный запуск этого шага обновляет существующий блок вместо его
дублирования), записывает его, запускает `nginx -t`, и если это
проваливается, **немедленно записывает обратно предыдущее
содержимое**, прежде чем вернуть ошибку -- живая конфигурация никогда
не остаётся в состоянии, не прошедшем валидацию, даже кратковременно.
Только после того как `nginx -t` проходит успешно, выполняется
`systemctl reload nginx`.

### Что этот мастер НЕ автоматизирует

Процесс из 7 шагов, из которого это было построено, никогда не
упоминал следующее, так что автоматизация этого означала бы
изобретение охвата, а не следование ему -- каждый из пунктов оставлен
как явный ручной шаг:

- **Создание собственной базы данных MySQL и пользователя сервиса.**
  `DATABASE_URL` записывается в сформированный `.env` пустым значением;
  создайте базу данных/пользователя самостоятельно, затем заполните
  через `service-env.html`.
- **TLS-сертификаты для каждого сервиса.** Предполагается, что
  wildcard-сертификат, покрывающий каждый поддомен
  `{label}.SERVICE_DOMAIN_ZONE`, уже существует
  (`NGINX_SSL_CERTIFICATE`/`NGINX_SSL_CERTIFICATE_KEY`); ничего здесь
  не вызывает certbot или любой другой процесс выдачи сертификатов.
- **Учётные данные YooKassa.**
  `YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY` оставлены пустыми, ровно
  как отмечал шаблон, на основе которого это было построено («вводятся
  вручную, опционально»).
- **Идентичности deep-link-ботов Telegram/MAX**
  (`SERVICE_TELEGRAM_BOT_USERNAME`, `SERVICE_MAX_BOT_DEEP_LINK_ID`)
  предполагаются фиксированными и общими для всех инстансов, исходя из
  единственного доступного примера на момент создания -- только
  параметр `?start=` выводится для каждого сервиса отдельно. Если это
  предположение неверно для конкретного сервиса, исправьте это позже
  через редактор `.env`; ошибиться в этом дёшево (сломанная
  deep-ссылка, а не сломанный деплой).

В продакшене этот сервис работает от собственного непривилегированного
пользователя Ubuntu, например `shaverma-admin` — никогда не от root.
Ничто в коде не предполагает root, и **имя пользователя не является
конфигурацией приложения**: приложение никогда не читает собственное
имя пользователя ОС, и `sudo` авторизует на основе реального UID
работающего процесса, а не чего-либо из `.env`. Нужно только, чтобы
оно совпадало между двумя местами на уровне ОС:

1. systemd-юнит, запускающий саму adminka — см.
   `deploy/shaverma-adminka.service`, `User=`/`Group=`;
2. правило sudoers ниже, выданное тому же пользователю.

Переименуйте `shaverma-admin` во что угодно в обоих местах вместе; в
`.env` менять ничего не нужно в любом случае.

`service.status` (только для чтения `systemctl show`), скрипт выдачи
учётных данных и `npm install`/`npm run build` (см. выше) не требуют
никаких повышенных привилегий вообще. Всё остальное, что затрагивает
принадлежащий root путь или сервис systemd/nginx, требует sudo, через
узко ограниченный allow-list, например
`/etc/sudoers.d/shaverma-admin-systemctl`:

```
shaverma-admin ALL=(root) NOPASSWD: \
  /usr/bin/systemctl start *-backend.service, \
  /usr/bin/systemctl stop *-backend.service, \
  /usr/bin/systemctl enable --now *-backend.service, \
  /usr/bin/systemctl reload nginx, \
  /opt/shaverma_adminka/backend/scripts/env_file_helper.py read *, \
  /opt/shaverma_adminka/backend/scripts/env_file_helper.py write *, \
  /opt/shaverma_adminka/backend/scripts/instance_files_helper.py create_tree *, \
  /opt/shaverma_adminka/backend/scripts/instance_files_helper.py install_backend *, \
  /opt/shaverma_adminka/backend/scripts/instance_files_helper.py install_dist *, \
  /opt/shaverma_adminka/backend/scripts/nginx_config_helper.py read, \
  /opt/shaverma_adminka/backend/scripts/nginx_config_helper.py write, \
  /usr/sbin/nginx -t, \
  /opt/shaverma_adminka/backend/scripts/systemd_unit_helper.py write *
```

(sudoers на самом деле не поддерживает продолжение строк внутри
одного правила так, как показано выше для удобства чтения -- пишите
это одной строкой либо как отдельные записи `Cmnd_Alias`/правила; в
любом случае проверьте перед установкой:
`visudo -c -f /etc/sudoers.d/shaverma-admin-systemctl`.)

Это выдаёт ровно то, что перечислено — и ничего больше, и каждый
аргумент скрипта-хелпера — это либо фиксированный литерал
(`nginx_config_helper.py` вообще не принимает аргументов), либо
`system_name`/имя юнита, проверенное на стороне приложения
собственной валидацией `unit_name_for()`
(`app/system/service_control.py`). Перед установкой правила
разверните **все четыре хелпер-скрипта** как **принадлежащие root, с
режимом `700`**, так чтобы `shaverma-admin` никогда не мог прочитать
или изменить их напрямую (только вызвать их, с повышением привилегий,
через этот конкретный грант):

```bash
for helper in env_file_helper instance_files_helper nginx_config_helper systemd_unit_helper; do
  sudo install -o root -g root -m 700 \
    "backend/scripts/${helper}.py" \
    "/opt/shaverma_adminka/backend/scripts/${helper}.py"
done
```

Затем отредактируйте собственные зашитые константы каждого скрипта в
соответствии с вашим реальным развёртыванием:

| скрипт                         | константа(ы)                        | должно совпадать с              |
|---------------------------------|--------------------------------------|-----------------------------------|
| `env_file_helper.py`            | `PROJECT_ROOT`                       | `INSTANCES_ROOT_DIR`              |
| `instance_files_helper.py`      | `PROJECT_ROOT`, `STAGING_ROOT`, `WORK_USER` | `INSTANCES_ROOT_DIR`, `INSTANCE_STAGING_DIR`, `SERVICE_WORK_USER` |
| `nginx_config_helper.py`        | `CONFIG_PATH`                        | `NGINX_CONFIG_PATH`               |
| `systemd_unit_helper.py`        | `UNIT_DIR`                           | фиксировано как `/etc/systemd/system`, это не настройка `.env` -- при необходимости изменяйте константу напрямую |

Эти константы -- никогда ничего, что присылает вызывающая сторона --
это то, что реально ограничивает каждое чтение/запись; несовпадение с
настройкой `.env`, с которой оно сопоставлено, безопасно (хелпер
просто смотрит не туда и падает с ошибкой, либо приложение
показывает/вычисляет устаревший путь), **за исключением**
`INSTANCES_ROOT_DIR`, который к моменту, когда мастер создания нового
сервиса пишет свежий блок nginx или юнит systemd, оказывается зашит
напрямую в конфигурацию этого сервиса -- см. врезку в «Мастер
развёртывания нового сервиса» выше.

Также создайте заранее, один раз, родительскую папку instances-root,
принадлежащую root и **проходимую для всех** (и nginx, и собственные
непривилегированные проверки статуса adminka должны иметь доступ в
неё):

```bash
sudo mkdir -p /opt/shaverma-instances
sudo chown root:root /opt/shaverma-instances
sudo chmod 755 /opt/shaverma-instances
```

**Если `deploy/shaverma-adminka.service` использует
`ProtectSystem=strict`** (по умолчанию да): это монтирует *всю*
файловую систему только для чтения для дерева процессов этого юнита,
и привилегированный хелпер, вызванный изнутри него через `sudo`, всё
равно наследует этот же вид только для чтения -- sudo меняет
uid/gid, но не пространство имён монтирования. Без `ReadWritePaths=`,
называющих каждую реальную цель записи (`INSTANCES_ROOT_DIR`,
`INSTANCE_STAGING_DIR`, директорию `NGINX_CONFIG_PATH` и `UNIT_DIR`),
редактор `.env` и каждый шаг записи мастера создания нового сервиса
падают с ошибкой доступа во время выполнения, даже несмотря на то, что
каждый из них корректно привилегирован на уровне приложения -- см.
комментарии в самом `deploy/shaverma-adminka.service`, где уже
перечислены все четыре.

Если `SYSTEMCTL_PATH`/`SUDO_PATH`/`ENV_HELPER_PATH`/
`INSTANCE_FILES_HELPER_PATH`/`NGINX_CONFIG_HELPER_PATH`/
`SYSTEMD_UNIT_HELPER_PATH`/`NGINX_BINARY_PATH` переопределены
относительно значений по умолчанию, обновите правило sudoers в
соответствии с ними.

## Заметки по безопасности

- Пароли: только Argon2id (`pwdlib`), никогда не сравниваются и не
  хранятся иначе.
- Токены (сессия, верификация OTP): генерируются через `secrets`,
  сравниваются через `hmac.compare_digest`.
- Коды OTP никогда не хранятся в открытом виде, только как
  HMAC-SHA256-дайджест с ключом `ADMIN_OTP_SECRET`; каждый challenge
  одноразовый и ограничен `ADMIN_OTP_MAX_ATTEMPTS` попытками.
- `/auth/login/start` и `/auth/login/verify` возвращают одну и ту же
  общую ошибку независимо от того, существует ли имя пользователя, так
  что эндпоинт нельзя использовать для перечисления администраторов.
- Базовое внутрипроцессное ограничение частоты запросов на обоих
  эндпоинтах входа (`app/core/rate_limit.py`). Это однопроцессный,
  находящийся в памяти лимитер — достаточно хорош для системы с двумя
  администраторами, работающей как один процесс, но **не**
  достаточен, если этот сервис когда-либо будет масштабирован на
  несколько инстансов; в этом случае сначала подставьте общий (например,
  на базе Redis) лимитер.
- CORS ограничен `FRONTEND_ORIGIN`.
- Кука сессии имеет флаг `Secure` только когда `APP_ENV=production` --
  проверьте, что это действительно установлено перед запуском в
  продакшн, это легко упустить, поскольку `.env.example` по умолчанию
  задаёт `development` для локальных копий.
- Нигде нет SQL, собранного конкатенацией строк (только SQLAlchemy
  ORM/Core), нет выполнения shell с несанированным вводом (см. слой
  system выше).
- Каждый запрос получает correlation id (заголовок `X-Request-ID`),
  который также прикрепляется к его записям в журнале аудита.
- `services.system_name` проверяется по безопасному шаблону
  идентификатора прежде чем когда-либо превратиться в имя юнита или
  быть переданным в `CommandExecutor` -- эшелонированная защита поверх
  того факта, что `CommandExecutor` вообще никогда не использует
  shell, так что поверхности для инъекций нет даже для значения, не
  прошедшего эту проверку.
- `service.start`/`service.stop` отказываются выполняться для юнита,
  который `service.status` сообщает как неустановленный
  (`LoadState=not-found`), так что некорректный или устаревший
  `system_name` вообще не может достичь `sudo`.
- `/services/{id}/start` и `/services/{id}/stop` требуют ту же сессию
  + CSRF-заголовок, что и `/auth/logout`; оба исхода (успех или
  ненулевой код завершения) логируются в аудит с разрешённым именем
  юнита, кодом завершения и длительностью.
- `env_file_helper.py` никогда не принимает путь файловой системы --
  только `system_name`, проверенный по тому же шаблону безопасного
  идентификатора, ограниченный константой `PROJECT_ROOT`, зашитой в
  сам скрипт (а не переданной вызывающей стороной). Грант sudoers
  вызывает только этот один скрипт с `read`/`write`; нигде нет
  `sudo cat`/`sudo tee`, что в противном случае позволило бы
  использовать грант для чтения или перезаписи любого файла,
  принадлежащего root, а не только `.env` сервиса `services`.
- `CommandExecutor` не даёт дочернему процессу никакого stdin
  (`DEVNULL`), если только спецификация явно его не предоставляет,
  вместо наследования stdin самого сервера -- `env.write` — единственное
  действие, которое когда-либо предоставляет содержимое stdin (новый
  файл, никогда не логируется).
- `env.write` отклоняет ключ, не являющийся допустимым именем
  переменной окружения, или значение, содержащее перевод
  строки/возврат каретки/NUL, прежде чем оно вообще достигает
  скрипта-хелпера; журнал аудита для успешной записи фиксирует, какие
  *имена* ключей были добавлены/удалены/изменены, никогда значения.
- UI редактора `.env` по умолчанию маскирует значения (поля ввода в
  стиле пароля, опциональный переключатель «показать значения») и
  запрашивает подтверждение перед сохранением, если правка удаляет
  какую-либо переменную.
- `instance_files_helper.py`, `nginx_config_helper.py` и
  `systemd_unit_helper.py` следуют тому же паттерну, что и
  `env_file_helper.py`: никогда не принимают путь файловой системы от
  вызывающей стороны, каждый путь строится из константы, зашитой в сам
  скрипт, `system_name` (где применимо) проверяется по тому же шаблону
  безопасного идентификатора.
- Загруженные zip-архивы распаковываются в процессе средствами Python
  `zipfile` -- никогда через подпроцесс (`unzip`), так что содержимое
  zip-архива не имеет вообще никакой поверхности для command-инъекций.
  Распаковка проверяет путь каждого элемента (отклоняет `..`/абсолютные
  пути/симлинки) и применяет лимит на общий размер и количество
  записей *до* того, как что-либо распаковывается, так что специально
  сформированный архив не может выйти за пределы целевой директории
  или исчерпать диск как zip-бомба.
- `npm install`/`npm run build` выполняются только в собственной
  непривилегированной директории staging adminka, никогда от root и
  никогда внутри принадлежащего root дерева инстанса (см. «Модель
  привилегий npm install» выше); фиксированный скрипт выдачи учётных
  данных точно так же непривилегирован.
- Конфигурация nginx никогда не остаётся в состоянии, не прошедшем
  `nginx -t`, даже кратковременно -- недействительная запись
  откатывается к предыдущему содержимому до того, как запрос вернёт
  ошибку (см. «nginx: никогда никакой частичной правки» выше).
- `service.enable_now` и `nginx.reload` — новые действия с повышением
  привилегий через sudo; `nginx.reload` и
  `nginx_config_helper.py read`/`write` вообще **не принимают никаких
  параметров** -- максимально безопасная форма гранта sudo, поскольку
  вызывающей стороне нечем повлиять.

## Тесты

```bash
cd backend
.venv/bin/pytest
```

Покрывает хеширование паролей, жизненный цикл challenge OTP (успех,
неверный код, истечение срока, исчерпанные попытки, повторное
использование после успеха), сессии (создание, истечение срока,
отзыв, выход), полный HTTP-процесс аутентификации (с замоканным
Telegram-клиентом — без реальных сетевых вызовов), запись журнала
аудита (включая то, что чувствительные ключи вычищаются),
`CommandExecutor` (stdout, stderr, код завершения, таймаут, усечение
вывода, работа с `cwd`/окружением -- они всегда запускают только
собственный интерпретатор Python теста, никогда реальную
административную команду), и слой управления сервисами целиком:
валидацию `unit_name_for`, построение CommandSpec для
`service.status`/`start`/`stop` (status никогда не использует sudo,
start/stop — всегда), обработку «не найден», и полный HTTP-процесс,
включая соблюдение auth/CSRF и логирование аудита; и слой редактора
`.env`: round-trip'ы парсинга/рендеринга (комментарии и пустые строки
сохраняются), диф добавления/изменения/удаления, валидацию
ключа/значения, `EnvFileControlService` (отсутствующий файл против
отсутствующей директории инстанса), построение CommandSpec для
`env.read`/`env.write`, и полный HTTP-процесс (включая то, что
успешное чтение/запись логируется в аудит только с именами ключей,
никогда со значениями).

Мастер создания нового сервиса покрыт на каждом уровне: построение и
валидация домена/punycode, создание строк в БД и проверки
уникальности, валидация загрузки zip-архива (обход путей, симлинки,
лимиты по размеру/количеству записей, отсутствующие
`frontend`/`backend`, безопасный повтор), построение argv/окружения и
парсинг вывода скрипта выдачи учётных данных, вызов
`npm install`/`build` и перенос `dist/`, рендеринг шаблона nginx и
идемпотентная логика вставки-или-замены в изоляции, оркестрация
nginx чтение/запись/валидация/**откат при неудаче**/перезагрузка в
изоляции (`NginxControlService`), и наконец полный HTTP-процесс целиком
(`test_provisioning_api.py`) -- создание, директории, загрузка, env,
сборка frontend'а, nginx, systemd, `GET .../provision/status` после
каждого шага, соблюдение CSRF/auth и содержимое журнала аудита,
включая то, что отклонённая конфигурация nginx действительно
откатывается, а дублирующиеся `url`/`system_name`/`bot_entry_key`
отклоняются с 409.

Всё вышеперечисленное (включая этот новый слой) выполняется против
единственного тестового дубля `FakeSystemctl` (`tests/conftest.py`),
который отвечает на `systemctl show`/`start`/`stop`/`enable`,
`nginx -t`/`reload`, `ss -Hltn`, скрипт выдачи учётных данных, `npm` и
все четыре привилегированных хелпера — `read`/`write`/`create_tree`/
`install_*` — из состояния в памяти (зеркалируя реальные директории во
временном `INSTANCES_ROOT_DIR`, где собственные проверки статуса
мастера должны их видеть) -- так что ничему из этого не нужны
настоящие systemd, sudo, nginx или принадлежащие root файлы на машине,
где выполняются тесты. Сами четыре хелпер-скрипта
(`backend/scripts/*_helper.py`) были проверены вручную от начала до
конца (ограничение путей, атомарная запись, сохранение
владельца/группы/режима, `daemon-reload`), а не через тестовый набор,
поскольку это самостоятельные привилегированные скрипты вне
собственного пути импорта приложения.
